# 07-death-respawn

_From the PDB research workflow (2026-08-20)._

**Verdict:** The game-over transition is entirely Blueprint and entirely game-mode-side: BP_GameModeBase_C::OnPlayerHealthDepleted, bound to the player pawn's UHealthComponent depleted delegate, is the single decision point, and a client has no game mode at all (verified live). The cleanest co-op design is therefore NOT to intercept the possession of BP_Pawn_GameOver_C but to remove that one delegate binding from every co-op player pawn (host included) and let the mod own death and respawn: strip in the existing SpawnDefaultPawnAtTransform hook (05DEC54C), backstop with FOnHealthDepletedDelegate::Broadcast (02B3F470) which doubles as the authoritative death event, corroborate with the bool& out-param of UHealthComponent::TakeDamage (015583E8), veto AController::Possess (016ACD68) for any non-AESPawn on a co-op controller, and respawn through the mod's existing UnPossess (0150A9F4) -> RestartPlayer (04A49BCC) -> destroy-corpse path with a full hitpoint/energy/cooldown reset. Because the interception sits on the delegate rather than the possession, the host's own death is handled identically and the session survives it — which is the requirement that rules out every alternative placement.

## Summary

DEATH IS 100% BLUEPRINT, AND 100% GAME-MODE — WHICH IS EXCELLENT NEWS FOR CO-OP.

The string "GameOver" does not exist in the exe (`strings -el ... | grep -i gameover` → only "GameOverride"). Every piece of the game-over flow lives in `BP_GameModeBase_C` (`/Game/Blueprints/Framework/BP_GameModeBase`), which subclasses AESGameModeBase. Verified live on the running host (console `status`): host `netmode=ListenServer gamemode=BP_GameModeBase_C`, client `netmode=Client gamemode=null`. **A client cannot run any part of the game-over flow.**

=== 3. STATE THAT MUST BE RESET ===
Respawning a FRESH pawn via RestartPlayer resets most transient state for free (empty FBuffableBool modifier stacks, fresh cooldowns, fresh damage parts). What is NOT free:
• Hull/armour/shield: the spawner (05DEEEE0) calls `ISavableInterface::StaticRestoreState(pawn, pawn->ShipData.GenericSaveData @FShipData+0x378, version @FShipData+0x3C8, true)` → `UHitpointComponent::RestoreState_Implementation` @05D7BDA8 restores the SAVED ratio. A respawned ship therefore comes back at whatever ratio was last saved. Set explicitly: reflected UFunction `SetCurrentHitpointsWithRatio` (exec thunk exists: `UHitpointComponent::execSetCurrentHitpointsWithRatio`) on Pawn+0x350 / +0x358 / +0x360 with 1.0f. It dispatches through vtable slot 153 (+0x4C8) to `UHealthComponent::SetCurrentHitpointsWithRatio` @01556948.
• PERSISTED hull damage: `FShipData.HealthRatio` (+0x360), `ArmorRatio` (+0x364), `UltimateRatio` (+0x368) and `FShipData.ShipItemInstance(+0x18)->UItem::Condition(+0x200)`. Reset these or the ship respawns wrecked (and the station repair bill is wrong).
• Equipment damage / damage parts: `UHealthComponent::RespawnDamageParts` @015185EC, `UHealthComponent::ResetDamageLimit` @0197A170, `UDeviceComponent::RespawnDevices` @017EFEDC.
• Weapon energy: `AWeaponBase::SetEnergyRatio(1.0f)` @02B432D4 for each weapon (WeaponComponent array at +0x238/+0x240, stride 0x50; energy at AWeaponBase+0xC04, max from `AWeaponBase::GetMaxEnergyCapacity` @012A03C8). Fire-rate cooldowns: `UWeaponComponent::ClearFireRateCooldowns` @02292090.
• Device cooldowns: `ADeviceBase::ClearCooldowns` @0195C110 for each device (DeviceComponent+0x390 array at +0xA0/+0xA8, stride 0x18, entry+0x10 = ADeviceBase*, per-device cooldown TArray<uint32> at device+0x4B8).
• Boost energy: ShipMovement (Pawn+0x378) + 0xAA8. ULT: `UGameplayLib::GetUltimateRatio` @05E323CC / `AESPlayerController::OnChangeULTRatio`.
• Consumables + secondary ammo: Inventory = FShipData.Inventory (Pawn+0x4B8+0x10); `UInventory::GetItemsOfCategory(9)` = consumables, `(1)` = secondaries (`UItem::Ammo` +0x1A0, `UItemLib::GetMaxAmmo`), `UConsumableComponent::RefreshPlayerConsumableSlot`.
• Control/kinematic stacks (only if you REVIVE the old pawn instead of respawning a new one): `HasControlsDisabled` FBuffableBool at AESPawn+0x1260, `IsInKinematicMode` at +0x1220. Pop with `AESPawn::PopDisableControls` @01426D70 / `AESPawn::PopKinematicMode` @016CDCD4 (FModifierHandle is an 8-byte struct passed BY POINTER as `const&`). Pushes: 01426F48 / 016CDDDC (return FModifierHandle in RAX, 8 bytes, no sret).
• The 88-byte volatile combat blob: `FShipSaveState` is UPlayerData+0x1D88, named `AncientDeviceShipSaveState` — a SINGLE global slot. `UGameplayLib::SaveShipState` @05E3A564 / `RestoreShipState` @05E3986C both go through `UGameplayLib::GetESPlayerPawn` @013F0CC0 (the host singleton) and UPlayerData, so they are **not per-player usable as-is**. `RestoreShipState(ctx, true)` sets Health/Armor/Shield to 1.0f and refills everything — its call list is the exact "make a ship playable" checklist; replicate it per-pawn, or temporarily make the singleton resolve to the target pawn (the mod already does this pattern for GetCurrentShip).

=== 4. HOST vs CLIENT ===
HOST-ONLY (never runs on a client, gamemode==null): the whole depletion block (client damage is already blocked at the funnel), `BP_GameModeBase_C::OnPlayerHealthDepleted`, all GameOver* state, BP_Pawn_GameOver_C spawn+possess, WG_GameOverScreen creation, ReviveRequest/HandlePlayerRevive/LoadCheckpointRequest/LoadMainMenuRequest. `AController::Possess` @016ACD68 is itself authority-gated at 016ACD8E-016ACDA1 (checks +0x338 bit2 / Role(+0x168)==3).
WHAT A CLIENT ACTUALLY SEES when the host destroys its ship:
  1. Actor destruction replicates → `APawn::Destroyed` @018357D8 → vtable +0x828 → `APawn::DetachFromControllerPendingDestroy` @018357F8 → `AController::PawnPendingDestroy` @01835844 → `AController::UnPossess` @0150A9F4 (NO authority guard) → `AESPlayerController::OnUnPossess` @05E1002C + BP `ReceiveUnPossess` + `OnPossessedPawnChanged` (AController+0x2D0) broadcast — all locally on the client.
  2. If the host possesses BP_Pawn_GameOver_C, `Controller->Pawn` (+0x2E8) replicates → `AController::OnRep_Pawn` @0493C740 → `AController::SetPawn` @016AC3B0 → AttachToPawn(233)/AddPawnTickDependency(235). `AController::SetPawn` does NOT broadcast OnPossessedPawnChanged and does NOT fire BP `ReceivePossess` (that only happens inside the server-only `Possess`). Since BP_Pawn_GameOver_C bReplicates=true, the client WOULD locally end up flying a non-AESPawn — every ES2 system that assumes AESPawn (HUD, weapons, movement) then misbehaves. This is what must never be allowed to happen.
  3. The client's own local HUD death path does NOT fire: `WG_HUD_TopLayer_C::PlayerJustDied` is bound to the local pawn's health delegate, and the mod's host→client ratio push uses `SetCurrentHitpointsWithRatio`, which (verified at 01556948 and 01556A24) only broadcasts `OnHitpointsChanged` (+0x350) and `OnHealthChanged` (+0x3F8) — it never touches `bHealthDepletedCalled`/`bOnDiedCalled` and never broadcasts OnHealthDepleted/OnDied. So a client at 0% hull shows an empty bar and nothing else.
  ⇒ The mod must SUPPRESS nothing on the client and SYNTHESIZE everything: a "you died / respawning in N" message, an input lock while dead, and the respawn confirmation. Existing string channel is enough.

=== 5. CLEANEST CO-OP DESIGN ===
Own the death entirely on the host; never let `BP_GameModeBase_C::OnPlayerHealthDepleted` run for ANY co-op player (host included). Two layers:
  LAYER A (surgical, no code hook, preserves explosion/loot/FX): for every player pawn the host spawns, walk the three `TMulticastScriptDelegate` invocation lists on its UHealthComponent (+0x3C8 OnPreHealthDepleted, +0x3D8 OnHealthDepleted, +0x3E8 OnDied) and remove the entry whose `FunctionName` == "OnPlayerHealthDepleted" and whose `Object` resolves to the game mode. Each entry is a 16-byte `TScriptDelegate` { FWeakObjectPtr Object (ObjectIndex int32 @0, ObjectSerialNumber int32 @4); FName FunctionName @8 }. The BP_ShipBase explode binding and the HUD binding stay in the same list, so the ship still blows up and the kill still looks right. Do this in the existing `AESGameModeBase::SpawnDefaultPawnAtTransform_Implementation` post-hook AND again on the next tick after possession (in case the GM binds late).
  LAYER B (belt-and-braces): hook `FOnHealthDepletedDelegate::Broadcast` @02B3F470 and, for a registered co-op pawn, skip the original when the list still contains the game-mode entry. Same hook is the mod's authoritative "player N died" event (RDX = dying actor, R8 = damage causer, R9 = killer controller, [RSP+0x20] = float).
Then the mod's own respawn: after a configurable delay (GM `MinRespawnDelay` at +0x358 is 1.0 live), reuse the existing loadout.cpp path — `AController::UnPossess` @0150A9F4 (only if a pawn survived) → `AGameModeBase::RestartPlayer` @04A49BCC with the mod's stashed per-player FShipDataState substituted into `UInventoryLib::GetCurrentShip` (already implemented) → `K2_DestroyActor` on the corpse → full health/energy/cooldown reset (§3) → tell the client "respawned". For "respawn at a partner", use `UGameplayLib::SpawnPlayerShip` @05E3EE5C at the partner's transform + `AController::Possess` @016ACD68 instead of RestartPlayer.
HOST DEATH: identical treatment — the host is player 0 in the same registry, so stripping the binding on the host's own pawn means the host's death never sets `GameOver` (+0x600), never spawns the game-over pawn, never creates the widget, and the session survives. That is the single most important consequence of putting the interception on the delegate rather than on the possession.
SAFETY NETS: keep a veto on `AController::Possess` @016ACD68 (if a registered co-op controller is about to possess a non-AESPawn, skip and schedule a respawn); and block `UUserFunctionsLib::LoadGame` @05E89DD4 / `AESPlayerController::ReturnToMainMenu` @05E164FC (the mod's existing `UGameplayStatics::OpenLevel` hook already covers LoadGame's tail).
