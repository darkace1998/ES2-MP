# 09-missions-loot-verification

_From the PDB research workflow (2026-08-20)._

**Verdict:** NEEDS_FIXES

## Summary

Adversarial verification of docs/research/05-missions-loot.md against sdk/symbols.tsv, tools/pdb_types.py and llvm-objdump on ES2-Win64-Shipping.exe.

WHAT HELD UP (independently re-derived, not taken on trust):
- Every single RVA in "Key functions", "Types" and "Hook plan" resolves to exactly the claimed demangled symbol. I checked all ~90 of them.
- Uniqueness: every RVA in the HOOK PLAN is unique (grep -c '^<RVA>\t' == 1). No ICF landmine in the plan itself. The only folded RVAs mentioned anywhere in the report are 0192E204 (ULootDropComponent::TickComponent, folded across 11 not 10 TickComponent bodies — correctly flagged as do-not-hook) and 05CA0514 (folded across execAddNonItemRewards + execAddNonItemRewardsByUI — NOT flagged by the report).
- All struct offsets I was asked to spot-check re-derive EXACTLY: UPlayerData MissionSaveState +0x3F8 (Num +0x400, Max +0x404, stride 0x140), CompletedMissions +0x1438, TrackedMainMission/SideMission/Job +0x160C/+0x1614/+0x161C, CustomWaypoint +0x1604, DialogCounterSaveState +0xB58, DialogLog +0x19D8 (Num +0x19E0), PlayingTimeSecondsDouble +0x2130, Credits +0x120, PlayerLevel +0x128; AMissionTaskBase MissionTaskID +0x2B0, LocationID +0x2B8, StationID +0x2C0, TaskState +0x2D8, ProgressValue +0x300, StageValue +0x304, TimeStamp +0x310, Attributes +0x318, delegates +0x378..+0x3D8, bEnableUpdatesOfPlayerData +0x3E8; AMissionBase Rewards +0x418, MissionType +0x400; FTaskSaveGameData size 0x140 / TaskID +0x30; FHUDTaskData size 376 with TaskData 0x0, OwningMissionID +0x140, TaskID +0x148, MissionTitle +0x150, ObjectiveText +0x160; AESPawn XP +0x3B8 / LootDrop +0x3A8; UXPComponent XP +0xA0 / NeededPlayerDamageRatio +0xA8; FItemState size 464. Several of these I confirmed a second time from the disassembly of UpdateTaskInPlayerData itself, which reads exactly those offsets.
- All ten enums (EMissionTaskState, EDialog, EDialogBehavior, EDialogSoundType, EIndicator, ERegisterIds incl. Challenge=33/MissionItem=38/MissionItemPOI=39, EInventoryCategory, ECreditsTransferType, EMissionType, plus vtable slots 238-242 on AMissionTaskBase and 229/230 on APickupBase) verified byte-exact.
- Claim 6 VERIFIED: APickupBase::APickupBase (01717C64, whole body 0x1717C64..0x1717FE8 plus its one cold block at 0x2A22E5C) never touches AActor+0x5B; bReplicates is indeed AActor+0x5B bit3.
- Claim 7 VERIFIED verbatim: AESHUD::ShowMissionTaskUpdate default-constructs FHUDTaskData (01311E0C), FHUDTaskData::operator= (017914A0), FindFunctionChecked, then ProcessEvent via vtable+0x278 (= UObject slot 79, confirmed), then FHUDTaskData::~ (017915B8). RCX=AESHUD*, RDX=const FHUDTaskData*.
- EnqueueDialog ABI VERIFIED exactly (float Delay really is in XMM3 while arg3 is a pointer in R8; EDialog at caller [rsp+0x20], EDialogBehavior [rsp+0x28], PlayOnce [rsp+0x30]).
- AddNonItemRewards ABI VERIFIED: RCX really is a hidden pointer to the 32-byte FMissionRewards, and RDX/R8 really are pointers to single enum bytes, R9 a const FName*.

WHAT DID NOT HOLD UP: nine substantive errors, one of them crash-grade (UItem::GetItemState's ABI is documented exactly backwards), one that silently mis-grants rewards (AddNonItemRewards does not touch faction standing at all), one that makes a client-side dialog gate a no-op (DialogCounter is NOT backed by UPlayerData+0xB58 at runtime), plus two missed call sites at the "one and only choke point" — one of which fires EVERY TICK — a real direct-write bypass of that choke point, and two entirely missing event sources (CompletedMissions and the Tracked* FNames) that the report tells you to mirror but gives you no hook for. Details in corrections.

## Corrections

- CRASH-GRADE / UItem::GetItemState ABI IS BACKWARDS. Report says: 'RCX = hidden return pointer for the 464-byte FItemState, RDX = this'. Reality (this is a MEMBER function, so the project's own rule this=RCX,sret=RDX applies): `python3 tools/disasm.py 0x05E9B940` -> `05e9b940 mov rdi, rcx` / `05e9b958 mov rcx, rdx` / `05e9b95b mov rbx, rdx` / `05e9b95e call FItemState::FItemState(void)` — i.e. RCX=this(UItem*), RDX=sret. Confirmed at a real call site inside UInventory::GetInventoryState: `llvm-objdump ... --start-address=0x145e9ae90` -> `145e9aea2: mov rcx, qword ptr [rsi]` (the UItem*) / `145e9aeaa: lea rdx, [rsp+0x20]` (the buffer) / `145e9aeaf: call 0x145e9b940`. Calling it as the report documents writes 464 bytes over a live UItem and reads a UItem header as a struct pointer. FIX: GetItemState(RCX=UItem*, RDX=FItemState* out). (CreateItemFromState 05E98820 IS correct as documented: `05e98857 mov rsi, rcx` — static, RCX=const FItemState*.)
- FALSE GRANT CLAIM / UMissionLib::AddNonItemRewards does NOT grant faction standing, and never touches OkkarCredits. Report (Key functions + Hook plan): 'Grants ... faction standing' and 'Client applies with ... UMissionLib::IncFactionGroupStanding (05E8089C)'. Reality: `python3 tools/disasm.py 0x05E71518 340 | grep call` yields exactly AddXP(05E209B8), ChangeCredits(05E21DF0), IncJobScore(05E80918), GetPlayerData, FindTaskInPlayerData, TLoadClassSynchronous, UClass::GetDefaultObject — no IncFactionGroupStanding. Cross-check: `xref 05E8089C` -> hits=1, only `05CA59BE UMissionLib::execIncFactionGroupStanding+0x24a`. What the code actually does: `05e7154b movd xmm0, dword ptr [rcx]` (Rewards.XP +0x00) -> AddXP; `05e7155f mov ecx, dword ptr [rbx+0x4]` (Rewards.Credits +0x04) -> ChangeCredits with `mov edx,0x5 / cmovne edx,r15d` gated on `cmp byte ptr [r14],0x2` — so ECreditsTransferType::JobReward(5) ONLY when *MissionType==EMissionType::Job(2), otherwise Undefined(0); `05e7157e mov ecx, dword ptr [rbx+0xc]` (Rewards.Standing +0x0C) -> **IncJobScore**, gated on `cmp byte ptr [rdi],r15b` (*FactionGroup != 0). Rewards.OkkarCredits (+0x08) is read by nothing. FIX the client replay to: AddXP(Rewards.XP) + ChangeCredits(Rewards.Credits, MissionType==2?5:0, true, false) + IncJobScore(Rewards.Standing) if FactionGroup!=0. Do not call IncFactionGroupStanding and do not mirror OkkarCredits from this hook.
- WRONG BACKING STORE / DialogCounter is not UPlayerData+0xB58 at runtime. Report: 'It gates on DialogCounter::TryInc (01841EF4), which is backed by UPlayerData::DialogCounterSaveState (+0xB58)'. Reality: `python3 tools/disasm.py 0x01841EF4` -> `01841f08 call 0x141842228 DialogCounter::GetSingleton`; `python3 tools/disasm.py 0x01842228` -> thread-safe-static init then `0184224c lea rax, [rip+0x816fefd] # 0x1499b2150` — a standalone process global at RVA 099B2150. `python3 tools/pdb_types.py layout sdk/raw/types.txt DialogCounter` -> `LF_CLASS DialogCounter sizeof=80` with a single member `0x0000 TMap<FName,int> CounterMap`.
